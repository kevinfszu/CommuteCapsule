# 通勤胶囊：功能与真实意图对齐评估

> 范围：仅做静态代码与设计文档审查，不做任何代码改动，不在本地编译（遵循仓库规则）。
> 结论基于可证实的实现行为，不评价视觉细节；提醒时序需真机验证的部分已在第 7 节标注。

## 0. 结论摘要

* **核心防坐过站链路是扎实的**：换乘站与终点站同级提醒、临近/到站/过站三阶段、响铃直到确认下车，且不依赖学习数据即可工作。
* **但意图里唯一被明确强调的"运用层"基本没做**：看板只给出"下车站还有几站/约几分钟"，**没有逐站到站时刻，也没有换乘下车、换乘上车、终点下车、出站、到达的预测时刻**；未来节点在时间轴上直接显示"—"。
* **打卡没有"逐级重算"**：站点打卡只更新本段下车站 ETA；节点打点只改变当前状态，不向上刷新"下一节点时刻 / 本段结束 / 全程结束"。你的补充要求是每打一次点，整条链都要实时收敛。
* **学习数据的口径与来源规则有实质偏差**：自动上车取的是"列车开动"而非你要求的"停稳"；机器推断（GPS/基站/时间）会进入学习样本，而人工补录反被排除；换乘上车时刻、全程时长两类数据没有学。
* **人工采集主线的可靠性不足**：出站无法在 App 里"现在打卡"，只能长按补录（且补录不参与学习）；刷闸机通知识别面窄，最可信的那条链路并不稳。
* 对齐度一句话：**提醒强、记录强、新建行程中、学习中、实时外推弱（且只做了单级）、趣味统计基本没有**。

## 1. 真实意图解构

### 1.1 五层结构

| 层次   | 你的原话要点                           | 可验收的功能契约                                          |
| ---- | -------------------------------- | ------------------------------------------------- |
| 目的层  | 防止睡着、走神导致坐过站                     | 到站前必须独立、可靠地提醒；不能依赖预测是否准确                          |
| 手段 A | 本次行程的进站/上车/打卡/换乘下车/换乘上车/终点下车/出站  | 8 类时刻可采集、可核对；**统一取"车辆到站刚停稳"**                     |
| 手段 B | 始发候车、站间、节点间、段乘车（含换乘）、全程          | 5 类时长可积累、可学习、可解释                                  |
| 运用层  | 打卡时刻 + 学到的时长 → 实时推算后面所有站点、所有关键节点 | **逐级重算**：下一站 → 下一节点 → 本段结束 → 全程结束；下一趟车只在**上车前**提示 |
| 交互层  | 打卡主要为了人工采集更准数据，次要为了趣味统计/成就感      | 低摩擦采集；数据可追溯；统计克制、不干扰主线                            |

### 1.2 一个关键澄清（来自你的回答）

> "进站/出站也归类为人工打卡，只不过不是人工点击 APP 按钮，而是人工手机刷站机。"

据此重新定义可信数据源：

* **可信（人工采集）**：App 按钮打点、手机刷闸机/刷卡的进站与出站、公交刷卡上车。
* **兜底（机器推断）**：GPS、基站/TAC、加速度、播报文本、按时间/剩余站数推算。

这条定义直接影响第 3.4、3.5 节的判定：**当前实现把"兜底"当"可信"来学习，把部分"人工补录"当噪声丢弃了。**

### 1.3 验收判据

* **J1 防坐过站闭环**：提醒是否独立于学习数据；到站/过站是否都能兜住。
* **J2 时刻完整性与口径**：8 类时刻是否都能落库；是否统一"停稳"口径。
* **J3 学习覆盖与来源**：5 类时长是否覆盖；样本是否来自可信人工源。
* **J4 实时外推与逐级重算**：一次人工打卡后，是否同时刷新"下一站 → 下一节点 → 本段结束 → 全程结束"四层时刻，而非只更新下车站一个 ETA。
* **J5 采集摩擦**：关键节点是否都能一键"记现在"；漏记是否可低成本修复。
* **J6 次要目的**：是否有克制的趣味统计/成就感反馈。

## 3. 逐功能对齐评估

### 3.1 新建行程

**意图期望**：以"最少输入跑起一趟"为优先，因为这条链路服务于人工采集；线路与上下车站是必要输入，但配置本身不应成为核心负担。

**现状**：

* 行程必须包含至少一条线路才能保存，见 [TripEditor.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/TripEditor.kt#L148-L164)。
* 线路选择完全依赖数据源：附近站点、线路列表、线路详情、地铁方向，见 [Pickers.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/Pickers.kt#L225-L229) 与 [Pickers.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/Pickers.kt#L500-L508)。
* 编辑页还包含定位预热提前量、唤起方式（按时间/离开出发地）、生效日期、班次带等，见 [TripEditor.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/TripEditor.kt#L172-L229)。

**判定：部分对齐。**

* 必要字段齐全，且为后续站数/ETA 提供基础，这是合理的。
* 但"先配数据源（导入线路或高德 Key）才能建行程"被放在核心链路最前面，与"打卡即采集"的主要目的冲突；配置复杂度更多是在支撑自动化（围栏唤起、班次推算），不是在支撑采集。

**影响**：首次使用门槛高；用户想快速记录一趟通勤时，被建卡流程劝退，直接损失样本。

### 3.2 乘车看板（核心）

**意图期望**：一个不打断的"防坐过站主界面"。至少要能回答四个问题：

1. 还有几站？（已知）
2. 下车站大概几点到？（已知，相对/绝对）
3. **换乘站、终点站、出站、到达分别大概几点？**（当前缺失）
4. 上车前，下一趟车何时到？（已知）

**现状（已对齐部分）**：

* 大字倒计时 + "当前站 / 下一站 / 距下车站还有 n 站"，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L1733-L1742)。
* 站点进度点、节点时间轴、到站打卡、"我知道了/我已下车"，见 [LiveBoard.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/LiveBoard.kt#L254-L347)。
* 换乘站与终点站共用同一套提醒，不因终点而降低强度，见 [AlightGuard.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/AlightGuard.kt#L19-L58)。
* 下一趟车：地铁按首末班 + 高峰/平峰间隔 + 学到的偏差推算，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L1185-L1202)；公交先实时、无车再用历史时刻表，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L1208-L1216)。上车后不再显示下一趟车，符合"仅在上车前提示"。

**现状（未对齐部分，且是关键）**：

* **时间轴上的未来节点一律显示"—"**，见 [LiveBoard.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/LiveBoard.kt#L609-L614)。这意味着"换乘下车 08:42""终点到站 08:58"这类信息用户看不到。
* **没有逐站到站时刻**。站点圆点只显示站名，不显示每站预计几点到，见 [LiveBoard.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/LiveBoard.kt#L289-L300)。
* **打卡后确实重算了，但只重算"下车站 ETA"**：`metroProgress` 以最近一次打卡为锚点，按学到的站间时长累加，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L1477-L1500)；它只更新了"下一站/下车站"这一层，没有向上一层更新下一节点、本段结束与全程结束。
* **节点打点没有级联**：写入节点后只更新 `stationAt/boardedAt/alightAt` 等状态并刷新当前看板，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L926-L936)；`LiveSnapshot` 也没有承载任何"未来时刻"的字段，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L33-L55)。
* 不存在"关键节点到达时刻"的推算与展示：换乘下车时刻、换乘上车时刻、终点到站时刻、出站时刻、到达时刻都没有预测值。

**判定：提醒链路强对齐；运用层（逐站 + 关键节点时刻 + 逐级重算）不对齐。**

**影响**：用户只能知道"还有 3 站/约 8 分钟"，无法据此判断"还有多久到换乘站""是否来得及""要不要提前收拾"。更关键的是，用户每打一次卡，期望看到的是"整条链的时刻向前收敛"，而当前只收敛了一个下车站倒计时。这正是原始意图第 4 条点名强调的能力，也是"防止坐过站"从"被动响铃"升级为"主动掌控"的关键。

### 3.3 行程记录

**意图期望**：完整记录本次 8 个时刻，可核对、可补录；作为趣味数据与成就感来源。

**现状**：

* 记录详情按节点列出时刻，推算值带"≈"；含行程段、到站打卡次数与打卡时刻；支持补录、删除，并回滚该记录写入的学习样本，见 [RecordsScreen.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/RecordsScreen.kt#L166-L202)。
* 列表显示起止时间与"全程 N 分钟"，见 [RecordsScreen.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/RecordsScreen.kt#L104-L118)。

**判定：对齐良好。**

**两点小偏差**：

* 到站打卡只显示"共 N 次 + 时刻"，不显示站名，难以回看"哪几站准、哪几站漏"。
* 补录值（BACKFILL）不参与学习，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L708-L737)。当用户事后补录时，数据只改善记录、不改善算法，和"主要为了采集更准数据"的定位相悖。

**未覆盖 / 偏差（重要）**：

1. **换乘上车时刻没学。** `TRANSFER` 学的是"上一段下车 → 本段上车"的时长，不是"换乘站列车何时到站/何时上车"的绝对时刻。意图明确要"上车（换乘）"的历史时刻用于下一趟车提示，现状换乘候车仍走排班 + 偏差，而不是历史时刻，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L1195-L1197)。
2. **全程时长没学。** 只在记录页显示"全程 N 分钟"，没有样本、中位数，也不参与预测，见 [RecordsScreen.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/ui/RecordsScreen.kt#L106-L110)。这也是 3.7 中"全程结束"这一级无法收敛的根因之一。
3. **样本来源规则与你的定义相反。** 学习只排除"补录/推算"，**自动推断（AUTO）仍然入选**，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L708-L721)。按你"刷闸机才算人工"的定义，GPS/基站/时间属于兜底，不该与人工样本同等学习。
4. **"停稳"口径不统一。** 自动地铁上车的判定基于"列车开动/离站"（`departureSince`）或位置移动，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L1308-L1338)；中途识别上车时更是直接用"开车时刻，不含站台候车"，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L2580)。而你要的是"车辆到站刚停稳"。这会让 `WAIT`、`TRANSFER` 系统性偏大一个停站时长。
5. **学习页只呈现"量"，不呈现"用"。** 见 [LearnReport.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/LearnReport.kt#L45-L57)。没有"这个时长用在了哪次预测、误差多少"，也没有跨行程趋势，成就感与可解释性不足。

**判定：覆盖度约七成；口径与来源两条有实质偏差；意图点名的两类数据（换乘上车时刻、全程）缺失。**

### 3.7 逐级重算：下一站 → 下一节点 → 本段结束 → 全程结束（新增要求专项）

**要求（按你的补充）**：任何一次人工打卡都不是"只改一个数字"，而是一次锚点更新，必须沿时间轴向上级联：

* **站点打卡（当前第 k 站）后**：更新 k+1 站 … 本段下车站的逐站到站时间；更新下一节点（换乘下车 / 终点下车）时刻；更新本段结束时刻；更新整个行程结束时刻。
* **节点打卡后**：更新下一节点时刻；更新本段结束时刻；更新整个行程结束时刻。

**应有的计算图**（从最近一次人工锚点出发，沿节点图正向传播，四层一次算完）：

```text
人工锚点（站点 k 的停稳时刻 / 节点时刻）
  ├─ L0 逐站：k → k+1 → … → 本段下车站
  │    每站用时：学到的站间区间 > 每站中位数 > 均分
  ├─ L1 下一节点：换乘下车 / 终点下车 / 出站 / 到达
  │    节点间用时：换乘步行、下车→出站、出站→到达
  ├─ L2 本段结束：本段下车站的到站时刻（L1 的第一个下游节点）
  └─ L3 全程结束：后续各段「等车 → 乘车 → 换乘 → 末段步行」逐段累加
```

每一层都复用已有学习产物：`stopPairSec` / `perHopSec`、`Learn.transferWalkSec`、`exitWalkSec`、`lastWalkSec`、`Learn.ride`、`BoardEst`。**数据已经存在，缺的是"串联 + 发布"。**

> 边界说明：站点打卡时，"下一节点"通常就是本段下车站，与 L2 重合；此时必须继续越过段边界，向"换乘上车 → 下一段下车 → 出站 → 到达"推导，否则会停在段边界、看不到全程结束。

**现状（逐层核对）**：

* **L0**：站点打卡只把锚点用于"已过几站 + 本段下车站 ETA"，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L1477-L1500)；只给下车站一个时刻，没有逐站列表。打卡确实会重置"提前发出的提醒阶段"，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L891-L901)，但这只影响提醒，不影响后续时刻的推算与展示。
* **L1/L2**：节点打点写入 `NodeLog` 并更新状态变量，但只影响当前段看板；没有计算并发布"下一节点 / 本段结束"的时刻。
* **L3**：`deadline` 看起来像"全程结束"，其实是服务存活截止时间（内部用），不随打卡刷新，也不是给用户看的预测，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L354-L369)。
* **承载层**：`LiveSnapshot` 只有当前大字、详情、站数、下车站名等字段，没有任何未来时刻字段，见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L33-L55)。
* **唯一接近"上游预测"的能力**是出发前的"地铁 + 公交换乘规划"（特定场景、出发前），见 [CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt#L1223-L1226)，不是通用级联。

**判定：只实现了 L0 的"下车站 ETA"一级，未级联到 L1/L2/L3，与新增要求不对齐。**

**影响**：打卡的价值被浪费。每打一次卡本应让"后面所有时刻"整体收敛，现在只能看到一个下车站倒计时；越接近换乘/终点，越需要"整条链的预计时刻"，而这正是缺失的。同时，L3 缺少"全程时长"学习样本，收敛精度也会受限（见 3.4 第 2 条）。
