# 通勤胶囊：自动学习与人工打卡机制

> 本文整理自关于「无人工打卡能否自动提醒」「自动学习与打卡如何配合」的讨论，对应代码版本 `0.4.36-local`。文中数值均来自当前代码常量，后续调整以实现为准。

## 0. 一句话结论

自动学习负责回答「这条线、这一段通常要多久」，给出基准；人工打卡负责回答「这一趟现在到哪、今天快慢如何」，提供锚点。到站提醒不依赖打卡，打卡是精度增强，不是开关。

## 1. 信号来源

| 信号 | 用途 | 依赖人工打卡 |
| --- | --- | --- |
| 高德线路详情 | 站点列表、站序、线路特征色、时刻表 | 否 |
| GPS / 沿线投影 | 公交已过站、到站距离、地铁贴站锚点 | 否 |
| 基站 / 地铁专网 | 地下无定位时的进出站、剩余时间推算 | 否 |
| 自动节点 `BOARD / ALIGHT / EXIT` | 每段起止时刻、学习样本切分 | 否 |
| 到站播报文字 | 「到了 / 即将到站」直接拉到到站阶段 | 否 |
| 到站打卡、`我已上车`、`我已下车` | 本次锚点、精确区间样本、上车时刻 | 是（增强项） |

## 2. 自动学习学什么

### 2.1 段级：这一段实际坐多久

- 每次本段结束自动记一条实乘分钟数，取中位数，最多保留最近 10 条。
- 合法范围 1–180 分钟。
- 用途：没有更细数据时，作为到站时刻的时间兜底。

代码：[Learn.recordRide / rideMin](../../app/src/main/java/com/busnotice/commute/Learn.kt#L171-L188)

### 2.2 公交沿线车速

- 按「沿线距离 ÷ 用时」得到米/分钟，指数平均（旧值 70% + 新样本 30%）。
- 只收 80–700 米/分钟的合理样本。
- 用途：公交在隧道、高架或定位抖动时，用速度外推剩余距离。

### 2.3 站间级：这一站到下一站多久

一次乘车结束时，把「上车时刻 + 到站打卡序列 + 下车时刻」切成区间：

- 相邻两站 → **精确区间样本**（A→B），每区间最多留 8 条，取中位数。
- 跨多站 → 只能算 **平均每站样本**，每线最多留 30 条，取中位数。
- 单个样本按站数校验，每站用时不在 40–600 秒的整段丢弃。
- 同时把本次站序并入该线路的完整站序，供「算法学习-线路」按行车方向列出区间。

代码：[RideStops.intervals](../../app/src/main/java/com/busnotice/commute/RideStops.kt#L46-L66)、[Learn.recordStops](../../app/src/main/java/com/busnotice/commute/Learn.kt#L414-L455)

要点：

- **没有中间站打卡也能学**：确认上车 → 我已下车 就是首末两站，只是只能落「平均每站」，落不了精确区间。
- 打卡越多，精确区间样本越全，区间明细中的「3.2 分钟 · 5 次」才有数据。

### 2.4 班次级

| 样本 | 来源 | 规则 |
| --- | --- | --- |
| 换乘站 / 始发站「几点上车」 | 只在人工确认上车或刷卡时记录 | 每天一条，最多 30 天，中位数；至少 2 天才启用 |
| 地铁班次偏差 | 手动点「已上车」时对比推算班次 | 残差指数平均，新样本占 30% |
| 个人反应时长 | 「提醒 → 点确认」的间隔 | 中位数，最终夹在 60–240 秒，默认 90 秒 |

这三类自动流程拿不到，属于「只有打卡才能学」的量。没有样本时退回时刻表 / 实时数据 / 默认 90 秒提前量。

### 2.5 行程级

- 全程时长、末段步行只在记录存在 `ARRIVE` 节点时写入。
- 出站后 30 分钟兜底结束的行程没有 `ARRIVE`，因此不学这两项，其余数据照常学。

### 2.6 学习何时落库

- 每段结束调用 `flushStopLearn(implicitOk = true)`，自动判定的下车同样触发，不要求人工操作。
- 行程结束或切换到下一段时结算；节点、打卡、站间样本一起写入。
- 「重新学习」按历史记录重放，先清空站间、上车时刻、实乘时长，再按保留下来的记录重建。
- 删除某条记录会触发同类重算。

## 3. 学到的值怎么用于实时推算

### 3.1 打卡锚点（本次行程）

有打卡时：

```
每站用时 = (最后一次打卡时刻 − 上车时刻) ÷ 打卡站序，夹在 45–300 秒
已过站数 = 最后一次打卡站序 + (当前时刻 − 打卡时刻) ÷ 每站用时
到下车站时刻 = 打卡时刻 + (总站数 − 打卡站序) × 每站用时
```

即把估算从「线路平均」切换成「这一趟的实际节奏」。没有打卡时，每站用时退回线路中位数。

代码：[RideStops.perHopSec / progress](../../app/src/main/java/com/busnotice/commute/RideStops.kt#L25-L44)

### 3.2 公交

- GPS 沿线投影得到已过站与剩余距离，结合学到的车速推算到站时刻。
- 人工打卡的站与投影结果取「更靠后」的那个，避免定位漂移导致进度后退。
- 投影超过 15 分钟未更新时，按车速 × 0.85 继续外推。

### 3.3 地铁

- 有定位时贴站作为锚点，按学到的每站秒数推进。
- 地下无定位时，用基站序列学到的「上车站 → 到达剩余时间」模型倒推。
- 地图/车机播报出现「到了 / 已到站 / 即将到站」时，直接校准，并立刻触发到站提醒。

## 4. 到站提醒链路

### 4.1 阶段判定

| 阶段 | 条件 | 文案 | 响铃 |
| --- | --- | --- | --- |
| `T1` | 剩余 0–1 站 | 下一站下车「XX」 | 20 秒一次，最多 8 次 |
| `AT` | 判定已到目标站 | 现在下车「XX」 | 15 秒一次，最多 8 次 |
| `OVERSHOOT` | 已过预计到站仍离站较远 | 「XX」已过站 | 20 秒一次，最多 3 次 |
| `NONE` | 已确认 / 离站很远 / 无数据 | — | 不响 |

判定优先级：已确认 `acked` > 过站 `overshoot` > 新鲜定位显示很远 `far` > 已到站 `atStation` > 剩余 0–1 站。

代码：[AlightGuard.kt](../../app/src/main/java/com/busnotice/commute/AlightGuard.kt#L19-L58)

### 4.2 「已到站」的几种判据

满足任一即可：

- 定位距下车站：地铁 ≤ 700 米；公交 ≤ 350 米 + 精度补偿（定位精度需 < 400 米）。
- 公交沿线投影只剩 1 站且距站 ≤ 600 米。
- 播报文字包含「到了 / 已到站 / 到站了 / 即将到达 / 即将到站」。
- 时间兜底：有可信时长、剩余 ≤ 1 站、已到预计时刻前 30 秒，且没有「新鲜定位显示 1.5 公里外」。

「新鲜定位显示很远」指 2 分钟内、精度 < 200 米、距离 > 1.5 公里；此时抑制提醒，避免刚上车就误报。

### 4.3 过站判定

- 地铁：超过预计到站 5 分钟，且距站 > 800 米。
- 公交：超过预计到站 3 分钟，且距站 > 500 米。
- 只有此前已经提醒过（T1/AT）才会进入过站阶段。

### 4.4 换乘与终点

换乘站和终点站共用完全相同的阶段、响铃间隔和响铃次数，终点站不降低强度。本段到站后中间段自动切下一段；末段到站后进入「前往目的地」，不再直接结束行程。

### 4.5 静音与确认

- 「我知道了」：静音当前阶段；阶段升级（T1 → AT → 过站）会重新响。
- 「我已下车」：结束本段提醒，切下一段或进入「前往目的地」。
- 已确认后不再重复提醒；确认状态会随运行状态一起持久化，进程重启不会重复弹「快到了」。

## 5. 人工打卡怎么配合

| 操作 | 本次行程的作用 | 是否写入学习 |
| --- | --- | --- |
| 到站打卡（中间站） | 替换每站用时、锚定已过站数 | 是：精确区间样本 + 站序 |
| 我已上车 | 确定上车时刻、启动乘车阶段 | 是：上车时刻、班次偏差 |
| 我已下车 | 结束本段、触发结算 | 是：实乘时长、站间样本 |
| 我知道了 | 只静音当前阶段 | 否 |
| 到站打卡后撤销 | 撤销后仍保留的打卡才参与学习 | 视是否保留 |

精度提升路径：

1. **锚点**：把「线路平均每站」换成「本趟实际每站」，ETA 立刻贴合当天节奏。
2. **样本**：中间站打卡才能产生 A→B 精确区间；没有打卡只有平均每站。
3. **防漂移**：公交打卡与 GPS 投影取更靠后者，定位漂移不会让进度倒退。
4. **补自动学不到的量**：上车时刻、班次偏差、反应时长只从人工事件学习。

## 6. 完全不打卡时会怎样

**仍可用的能力**

- 自动开始行程、自动判定上车/下车/出站。
- 换乘下车提醒、终点站提醒、过站提醒。
- 线路级站间中位数、实乘时长、公交车速持续自适应。

**会退化的场景**

| 场景 | 影响 |
| --- | --- |
| 第一次坐某条线/某个方向 | 没有站间时长和基站模型；地铁地下按时间/站数估，可能早或晚一站 |
| 线路数据缺失或候选不匹配（区间车、临时改线） | 没有站序，剩余站数 = -1，只剩按时间的到站兜底，没有「下一站」倒数 |
| 自动上车判定失败 | 不进入乘车阶段，本次没有车上提醒（提醒的前提是行程已开始且已判定上车） |
| 定位/后台受限 | 信号变旧，退化为时间估算；「新鲜定位显示很远」会抑制误报，但断信号太久精度下降 |
| 通知权限关闭 / 服务被杀 | 提醒无法展示；重新打开后按持久化状态恢复，不会重复弹已确认的提醒 |

## 7. 30 条记录、30 天与「固定保留」

这里有**两层存储**，不要混为一谈：

| 层 | 规则 | 是否参与重建 |
| --- | --- | --- |
| 历史行程记录 | 最多 30 条、只留 30 天；固定的记录额外保留且不占名额、不过期 | 是 |
| 常驻学习样本 | 每线平均每站 30 条、每区间 8 条、每段实乘 10 条、上车时刻 30 天 | 重建时清空后按历史重放 |

### 7.1 停止打卡后，精度会怎样

- **精确区间样本**：后续不打卡不会新增，也不会覆盖；每区间最多 8 条，前 5–10 次完整打卡基本已满。它不会变差，只是停止增长。
- **平均每站 / 实乘时长 / 公交速度**：每趟都会更新，旧样本被新样本滚动替换；这是跟随近期路况自适应，不是精度下降。
- **上车时刻 / 班次偏差 / 反应时长**：只从人工事件学习。不打卡后数值冻结，短期不变差，长期不再跟随新作息或新时刻表。
- **单次行程体感**：失去「本趟打卡锚点」，ETA 退回线路中位数 + GPS/基站/时间推算，可能早或晚一站。

### 7.2 真正的风险在「重建」

如果每天两趟，约 15 天后完整打卡的行程会滚出 30 条历史。此时：

- 点「重新学习」或删除任意记录触发重算；
- 重算会先清空站间样本、上车时刻、实乘时长，再按剩余历史重放；
- 剩余历史全是无打卡记录 → 精确区间、上车时刻等样本永久回退到「无打卡版本」。

日常不做重建时，常驻样本库不受历史淘汰影响。

### 7.3 固定保留如何解决

- 行程记录列表每行右侧星标、详情页底部按钮，可把记录固定。
- 固定的记录：
  - 不占 30 条名额，作为额外记录长期保留；
  - 不受 30 天过期清理；
  - 仍可手动删除，删除时学习样本照常回滚；
  - 会被「重新学习」一起重放，因此可以保住那几趟高质量打卡行程的精确区间样本。
- 固定条数当前不设上限。

## 8. 建议的使用方式

1. 前 5–10 次尽量完整打卡，包含中间站，让精确区间样本先长出来。
2. 这批记录完成后逐条固定（星标），防止滚出 30 条。
3. 之后可以不打卡，线路级中位数会继续自适应。
4. 长期不打卡时，避免点「重新学习」；确需重建，先把关键记录固定。
5. 如果希望区间样本保持新鲜，可每 20–30 趟补一次中间站打卡。
6. 到站提醒始终可用；但地铁地下首趟或线路数据异常时，建议保留人工留意到站。
