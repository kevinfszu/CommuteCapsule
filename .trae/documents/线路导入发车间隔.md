# 线路导入支持高峰/平峰发车间隔

## Summary

高德的 `timedesc` 是唯一能拿到分时段发车间隔的字段。本次改造：

1. 修复高德 `timedesc` 解析：支持 `day_type = all`、同一组同时含 `weekday/weekend`，不再丢数据。
2. 修复首末班回退：`start_time` / `end_time` 为空或非法时，用 `timedesc` 的最早开始、最晚结束推算，最后才用 06:00 / 23:00。
3. 「用高德生成」页新增可编辑的「发车间隔」分时段表：工作日、周末各一张，可改起止时间、逐段改间隔、增删时段；高德没返回 `timedesc` 时也从空表开始手填。
4. 「线路详情」页新增同样的分时段表，已导入线路可随时查看和修改。
5. 把 `service` 的 8 段上限放宽到 24 段，避免 16 段的公交线路被截断。

不改变行程引擎的推算逻辑，只补齐导入与编辑的数据链路。

## Research Findings

### 官方文档

- 高德「公交信息查询」接口：`https://restapi.amap.com/v3/bus/linename`，`extensions=all` 才返回详细信息。
- 文档对关键字段只有一句话说明：
  - `start_time`：首班车时间
  - `end_time`：末班车时间
  - `timedesc`：线路详细时间，内容为 JSON 串，需要解码并做内容解析
- 官方没有给出 `timedesc` 的内部结构、`day_type` 取值、`interval_time` 格式，也没有提到 `peak_time_group` / `low_time_group` / `flat_time_group`。

### 实际 API 返回（用设备里已保存的 Key 做只读 GET 验证）

- 地铁 13 号线两个方向：
  - `start_time`、`end_time` 都是空字符串。
  - `timedesc` 解码后：`rule_group` 里 `day_type=["weekday"]` 有 4 段、`["weekend"]` 有 3 段；每段为 `start_time` / `end_time` / `interval_time`，格式都是 `HH:mm:ss`（如 `"interval_time":"00:06:00"`）。
  - 另有 `allRemark` 是给人看的摘要（「工作日 06:00-09:00 6分钟/趟 …」）。
- B1 路（公交）：`timedesc` 为空，`start_time=0600`、`end_time=2230`，没有任何分时段间隔。
- 南 1 路 B：一组 `day_type=["weekday"]`，另一组 `day_type=["weekend","weekday"]`，表示同一组时段同时适用于工作日和周末。
- 乐平 01B 路：`day_type=["all"]`，共 16 段。
- 所有样本里 `peak_time_group` / `low_time_group` / `flat_time_group` 都是空数组，且无官方说明，不能作为数据来源。

### 对当前代码的影响

- `AmapData.serviceOf` 只把含 `weekday` 的组放进工作日、含 `weekend` 的放进周末；`["weekend","weekday"]` 只会进工作日（周末靠引擎「周末为空复制工作日」兜底），`["all"]` 被直接丢弃。
- `AmapData.parseHits` 只用 `start_time` / `end_time`，空值直接回退 06:00 / 23:00，13 号线会丢掉 `timedesc` 里的 06:00–22:30、06:03–23:05。
- `JsonTransit.parseService` 最多只读 8 段，16 段的线路会被截断。
- 「用高德生成」和「线路详情」都没有展示或编辑 `service`，用户无法核对或补充间隔。

## Proposed Changes

### 1. AmapData.kt：解析与生成

1. `Hit` 增加两个字段（默认空表，保持现有构造兼容）：

```kotlin
val weekdayBands: List<HeadwayBand> = emptyList(),
val weekendBands: List<HeadwayBand> = emptyList(),
```

2. 新增生成用的覆盖参数：

```kotlin
data class ServiceBands(
    val weekday: List<HeadwayBand>,
    val weekend: List<HeadwayBand>,
)
```

3. `parseHits` 每条记录：
   - 先 `val (wd, we) = parseTimedesc(o.optString("timedesc"))`。
   - `firstMin = hhmmToMin(start_time) ?: wd.plus(we).minOfOrNull { it.from } ?: 6 * 60`
   - `lastMin = hhmmToMin(end_time) ?: wd.plus(we).maxOfOrNull { it.to } ?: 23 * 60`
   - `end_time` 为 `0000` 时按 1440 处理，避免末班变成 00:00。
   - 写入 `weekdayBands = wd`、`weekendBands = we`。

4. `serviceOf` 改为 `parseTimedesc(timedesc: String): Pair<List<HeadwayBand>, List<HeadwayBand>>`：
   - URL 解码 → `JSONObject` → 遍历 `rule_group`。
   - 对 `date.day_type` 的每个值：
     - `weekday` → 追加到工作日
     - `weekend` → 追加到周末
     - `all` → 同时追加到工作日和周末
     - 其他值忽略
   - 每组 `time_group`：`start_time` / `end_time` / `interval_time` 都按 `HH:mm:ss` 解析；`to > from`、间隔 30–1800 秒才收。
   - 每个列表按 `from` 排序、按 `(from,to,headwaySec)` 去重，最多保留 24 段。
   - 解析失败或空表返回 `emptyList()`，不抛异常。
   - 保留注释说明：`peak_time_group` / `low_time_group` / `flat_time_group` 实际为空且官方无说明，暂不使用。

5. `buildLines` 增加可选参数：

```kotlin
service: ServiceBands? = null,
```

   - 未传时用该方向 `Hit` 自带的 `weekdayBands` / `weekendBands`。
   - 传入时两个方向统一使用传入的 `ServiceBands`。
   - 任一列表非空才写 `service` 对象，格式保持 `{ "weekday": [...], "weekend": [...] }`，`band` 仍为 `{ from, to, headwaySec }`。
   - 空周末写空数组，沿用「周末为空复制工作日」的既有语义。

### 2. JsonTransit.kt：放宽段数、支持写回

1. `parseService` 的 `minOf(arr.length(), 8)` 改为 `minOf(arr.length(), 24)`。

2. `updateLineParams` 增加可选参数：

```kotlin
service: Pair<List<HeadwayBand>, List<HeadwayBand>>? = null,
```

   - `null`：保持原 `service` 不动，现有调用行为不变。
   - 非 `null`：替换该线路所有方向记录的 `service`；两个列表都为空时移除 `service` 字段。
   - 写入后仍调用 `parse(updated)` 做整体校验。

3. 新增私有 `bandsJson(bands)` 与 `serviceJson(wd, we)`，统一生成 `{from,to,headwaySec}` 数组。

### 3. Transit.kt / ImportedJsonSource.kt：透传

- `Transit.updateImportedLine` 增加 `service: Pair<List<HeadwayBand>, List<HeadwayBand>>? = null`。
- `ImportedJsonSource.updateLine` 同样增加并在调用 `JsonTransit.updateLineParams` 时传入。
- 默认值保证现有调用（如有）不需要改。

### 4. 新增 `ui/HeadwayBandsEditor.kt`

一个可复用组件，供导入页和详情页共用：

```kotlin
@Composable
fun HeadwayBandsEditor(
    bands: List<HeadwayBand>,
    onChange: (List<HeadwayBand>) -> Unit,
    enabled: Boolean = true,
    modifier: Modifier = Modifier,
)
```

- 每一段一行：
  - 第一行：开始时间输入框、`–`、结束时间输入框、右侧圆形删除按钮（`RoundButton(size = 32.dp)`，`×`）。
  - 第二行：`HeadwayStepper("间隔", b.headwaySec) { ... }`，复用现有组件。
  - 时间输入用本文件内的紧凑 `CompactTimeField`：`BasicTextField`，宽约 64dp、高 36dp，只允许数字和 `:`、最多 5 个字符，占位 `HH:mm`。
- 列表下方 `PillButton(secondary = true)`：`＋ 添加时段`。
  - 新段默认接在最后一段之后：`from = 上一段.to`，`to = min(from + 60, 1440)`，`headwaySec` 沿用上一段或 360；空表时给 `06:00–24:00 / 360`。
- 同一文件提供校验函数：

```kotlin
fun checkBands(bands: List<HeadwayBand>): Pair<List<HeadwayBand>?, String?>
```

  - 时间必须能解析成 `HH:mm`，`to > from`，间隔 30–1800 秒。
  - 按 `from` 排序后检查相邻段 `next.from < prev.to` 视为重叠，返回错误文案。
  - 允许段与段之间留空档（引擎会按最近一段推算）。
  - 空表返回 `emptyList<HeadwayBand>() to null`，表示不提供间隔。

## Assumptions & Decisions

- 按用户选择：导入页展示并可逐段修改；`timedesc` 缺失时提供完整可增删的分时段表；线路详情页可查看并修改。
- 高德有数据时以高德为初始值，用户可改；高德没数据时从空表开始，不强制填写。
- 同一线路两个方向共用一份发车间隔：导入时以选中方向为基准（选中为空则用反向），详情页编辑后同时应用到两个方向；各方向首末班仍独立。
- 周末为空表示「与工作日相同」：生成时不写周末数组，界面用开关表达；关闭开关后显式写入周末表。
- 首末班优先级：高德 `start_time/end_time` → `timedesc` 边界 → 06:00 / 23:00。
- `peak_time_group` / `low_time_group` / `flat_time_group` 在实测中始终为空且官方无定义，本次不解析。
- 分段上限 24，避免 16 段线路被截断，同时防止异常数据无限增长。
- 不新增页面，不改变行程引擎、候选生成和 `service` 的既有语义。
