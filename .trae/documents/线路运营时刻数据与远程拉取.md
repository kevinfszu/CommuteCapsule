# 线路运营时刻数据与远程拉取

## 1. 摘要

把线路数据从「站序 + 坐标 + 单一首末班」扩展为可表达的运营时刻：

* 工作日 / 周末各一张**分时段发车间隔表**（band 列表），每段含起止时间与间隔；
* 间隔内部统一用**秒**，界面按「分 + 秒」两行设置，支持 5 分 20 秒这类官方值；
* 每个方向**始发站**的首班车、末班车时间，其余车站按站序推算，站点可单独覆盖；
* 添加地铁时自动带出该方向的时段表与首末班；已添加的行程可**逐段**修改间隔（分 + 秒），时段沿用线路数据；
* App「数据源」新增「从链接拉取」，填一个 JSON 地址即可更新线路数据。

## 2. 高德「公交信息查询」实测结论（2026-11-19）

已用用户提供的 Key 实测 `/v3/bus/linename?city=440100&extensions=all` 与 `/v3/bus/lineid`，原始响应只落在本地 `data/amap/`（`/data/` 已在 `.gitignore` 中，不进仓库）。

### 2.1 `timedesc` 是真实可用的分时段间隔

`timedesc` 是 URL 编码的 JSON，结构为 `rule_group[].date.day_type`（weekday / weekend）+ `time_group[]`（`start_time` / `end_time` / `interval_time`，精确到秒），另有 `allRemark` 文本。

**13 号线（新沙 → 天河公园）**

| 类型 | 时段 | 间隔 |
| --- | --- | --- |
| 工作日 | 06:00–09:00 | 6 分（360 秒） |
| 工作日 | 09:00–17:00 | 7 分（420 秒） |
| 工作日 | 17:00–20:00 | 9 分（540 秒） |
| 工作日 | 20:00–22:30 | 11 分（660 秒） |
| 周末 | 06:00–10:00 | 8 分（480 秒） |
| 周末 | 10:00–20:00 | 6 分（360 秒） |
| 周末 | 20:00–22:30 | 8 分（480 秒） |

反向（天河公园 → 新沙）：分段界点相同，首班 06:03、末班 23:05，间隔一致。

### 2.2 11 号线没有 `timedesc`

* 内环（赤沙）：`0614–2256`，32 站（首尾重复，去重 31）；
* 外环（龙潭）：`0610–2256`，31 站；
* `/v3/bus/linename` 与 `/v3/bus/lineid` 两种查询的 `timedesc` 都是空字符串，只有 `start_time` / `end_time` 作为线路级首末班。

### 2.3 其他发现

* 13 号线二期（鸦岗—天河公园）`status=3`、`timedesc` 为空，截至 2026-11-19 未开通。
* 11 号线含广州火车站（暂缓开通），13 号线为 15 站运营段；数据按「当前运营版」生成。
* 坐标为 GCJ-02，需转 WGS-84；站序与现有数据仅在 13 号线「西洲 / 槎龙」顺序不同，按高德顺序。

### 2.4 结论

| 字段 | 11 号线 | 13 号线 |
| --- | --- | --- |
| 站序 / 坐标 / 环线 / 反向 id | 可用 | 可用 |
| 双向始发站首末班 | 可用（`start_time` / `end_time`） | 可由 `timedesc` 首末段推出 |
| 工作日 / 周末分时段间隔 | 无，用官方新闻值 | 可用，4 段 / 3 段，精确到秒 |

因此数据结构必须是**分时段表**，不能只保留「高峰 / 平峰」两档。

## 4. 数据格式（v2）

在现有 JSON 上新增可选的 `service`，并明确 `first` / `last` 的语义。

```json
{
  "region": "gz",
  "meta": {
    "source": "广州地铁官网 + 官方新闻稿 + OpenStreetMap",
    "updated": "2026-11-19",
    "note": "11 号线间隔取自官方新闻稿，时段为估算；13 号线时段与间隔取自高德 timedesc"
  },
  "lines": [
    {
      "id": "gz13-xinsha-tianhe",
      "name": "13号线",
      "subway": true,
      "loop": false,
      "dirLabel": "新沙",
      "reverseId": "gz13-tianhe-xinsha",
      "first": "06:00",
      "last": "22:30",
      "hopSec": 140,
      "service": {
        "weekday": [
          { "from": "06:00", "to": "09:00", "headwaySec": 360 },
          { "from": "09:00", "to": "17:00", "headwaySec": 420 },
          { "from": "17:00", "to": "20:00", "headwaySec": 540 },
          { "from": "20:00", "to": "22:30", "headwaySec": 660 }
        ],
        "weekend": [
          { "from": "06:00", "to": "10:00", "headwaySec": 480 },
          { "from": "10:00", "to": "20:00", "headwaySec": 360 },
          { "from": "20:00", "to": "22:30", "headwaySec": 480 }
        ]
      },
      "stops": [
        { "name": "新沙", "lat": 23.1011, "lng": 113.5852 },
        { "name": "天河公园", "lat": 23.1245, "lng": 113.3702 }
      ]
    }
  ]
}
```

规则：

* `first` / `last`：**该方向始发站**（`stops[0]`）的首班、末班发车时间。站点时间 = 始发站 + `站序 × hopSec`；站点自带 `first` / `last` 时以站点为准。环线以记录第一个站为始发站。
* `service.weekday` / `service.weekend`：band 数组，按时间升序，`from < to`；`from` / `to` 为 `HH:mm`，允许 `24:00` 表示当天结束。
* `headwaySec`：发车间隔，**单位秒**，整数，限制 30–1800（5 分 20 秒 = `320`）。
* `weekend` 缺省时复制 `weekday`。
* `service` 整体缺省：地铁按高峰 360 秒 / 平峰 540 秒，非地铁按 600 / 900，高峰时段默认 `07:00-09:30`、`17:00-19:30`；由代码合成 5 段全覆盖的 band（见 5.1），保证任何时刻都能取到间隔。
* 全部 band 非法（缺字段、`from >= to`、`headwaySec` 越界）视为没有 `service`，走默认值，不报错。
* `service` 最多 8 段/天，超出的段忽略。
* 旧格式（无 `service`、无站点首末班）继续可解析，行为与现在一致（站点首末班改为按站序推算）。
* 时间计算用「一天中的分钟」：`06:00` = 360，`24:00` = 1440；起点超过 1440（如 `24:30`）按 1470 存，用于跨零点末班。

## 5. 代码改动

### 5.1 `Model.kt`

新增 band 类型与 `Candidate` 字段（都带默认值，旧构造不受影响）：

```kotlin
/** 一段发车间隔：from/to 为一天中的分钟，to 允许 1440（24:00） */
data class HeadwayBand(val from: Int, val to: Int, val headwaySec: Int)

data class Candidate(
    ...
    val weekdayBands: List<HeadwayBand> = emptyList(),
    val weekendBands: List<HeadwayBand> = emptyList(),
)
```

新增辅助函数：

```kotlin
fun Candidate.bandsFor(weekend: Boolean): List<HeadwayBand>   // 周末为空时回落工作日；都为空时用 headwayMin/offPeakHeadwayMin 合成
fun Candidate.headwaySec(minOfDay: Int, weekend: Boolean = false): Int
fun Candidate.peakHwSec(weekend: Boolean = false): Int        // band 里最小的间隔（展示用）
fun Candidate.offPeakHwSec(weekend: Boolean = false): Int     // band 里最大的间隔（展示用）
fun Candidate.scheduleText(): String                          // 「工作日 6–11 分钟 · 周末 6–8 分钟」/「约 6 分钟一班」
```

`bandsFor` 的合成规则（band 与旧分钟字段都为空时）：

* 地铁：高峰 360 秒、平峰 540 秒；非地铁：600 / 900。
* 工作日：`00:00–07:00` 平峰、`07:00–09:30` 高峰、`09:30–17:00` 平峰、`17:00–19:30` 高峰、`19:30–24:00` 平峰。
* 周末：复制工作日。
* 旧记录仅有 `headwayMin` / `offPeakHeadwayMin` 时，平峰取 `offPeakHeadwayMin × 60`（为 0 则 `peak × 1.5`）。

`headwaySec`：取包含 `minOfDay` 的 band；落在第一段之前 → 第一段间隔；落在最后一段之后 → 最后一段间隔（保证不返回 0）。

`peakHw()` / `offPeakHw()` 保留（分钟展示），改为 `(peakHwSec() + 59) / 60` / `(offPeakHwSec() + 59) / 60`。

`toJson` / `fromJson`：

```kotlin
.put("weekdayBands", bandsText(weekdayBands))   // "360-540:360,540-1020:420"
.put("weekendBands", bandsText(weekendBands))
```

* `bandsText` / `parseBands` 双向转换，空列表写 `""`；解析非法项跳过。
* 旧记录没有这两个键 → 空列表，运行时 `bandsFor` 合成，行为不变。

### 5.2 `Decision.kt`

```kotlin
fun headwayAt(minOfDay: Int, weekday: Boolean, bands: List<HeadwayBand>): Int   // 秒
fun isPeakAt(minOfDay: Int, weekday: Boolean, bands: List<HeadwayBand>): Boolean // 当前段间隔 == 当天最小间隔

fun metroSchedule(nowSec: Int, firstMin: Int, lastMin: Int, weekday: Boolean,
                  bands: List<HeadwayBand>, n: Int = 2, graceSec: Int = 0): List<Int>

fun metroResidual(nowSec: Int, firstMin: Int, lastMin: Int, weekday: Boolean,
                  bands: List<HeadwayBand>): Int?
```

* `metroSchedule` 改为 `t += headwayAt((t / 60) % 1440, weekday, bands)`（秒，不再 ×60）。
* `metroResidual` 直接用 `headwayAt` 的秒值。
* `metroAdvice` 展示「约 X 分钟一班」时用 `candidate.headwaySec(当前分钟)`；`nextCatchable` 保持 `headwayMin * 60`（无时间上下文，取最小段即可，创建候选时会把 `headwayMin` 写成最小段分钟）。
* 已有测试的 `metroSchedule(..., true, 5, 10)` 改为传 `bands(300, 600)` 辅助函数（见第 8 节），断言值不变。

### 5.5 `RemoteTransit.kt`（新建）

```kotlin
object RemoteTransit {
    suspend fun fetch(url: String): String   // 必须在 IO 线程调用
}
```

* 只接受 `http://` / `https://`，其他协议抛「只支持 http/https 地址」。
* `connectTimeout = 8000`、`readTimeout = 15000`、跟随重定向。
* `Accept: application/json`，自定义 User-Agent。
* 最多读 2 MiB，超出中断并报错。
* 非 200 或内容为空时抛出带状态码的中文异常。

## 9. 假设与决策

* 间隔与时段用 band 表表达，不再限定「高峰 / 平峰」两档；13 号线按 4 段 / 3 段原样落数据。
* 时段起止只读，只改间隔：用户明确只需要「分 + 秒」设置；时段增删改留到以后。
* 11 号线无 timedesc：用官方新闻的 320 / 450 / 374 秒，时段估算并标注待核对；用户可在 App 内逐段改。
* 首末班按始发站推算，减少数据量；有大小交路或特殊末班时用站点级 `first` / `last` 覆盖。
* 高德只用于开发期整理数据：Key 存本地文件、原始响应不入仓库；发布数据以官网/新闻稿为准核对，App 不直连高德。
* 默认数据地址留空，避免把私有地址写死；构建时可用 `TRANSIT_DATA_URL` 注入。
* 只做手动拉取，不做后台自动更新。
* 向后兼容：旧 JSON、旧 `Candidate` 记录、`MockSource` 不改数据即可运行。
