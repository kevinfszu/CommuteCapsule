# 界面文案规范化方案

## 一、概述

将应用中所有用户可见的标题、按钮、提示、通知与错误文案统一为一套「正式、精准、简洁」的表达，并统一术语。范围按用户确认：**全部（含演示回放与错误提示）**；术语允许规范化调整（如「通勤车」→「通勤班车」）。

本方案只改文案，不改交互逻辑、布局与视觉。实现方式为直接修改 Kotlin 中的中文字符串常量（不迁移到 `strings.xml`），并同步修正受影响的单元测试断言。

## 二、现状分析

- 文案全部硬编码在 Compose 代码与少量资源文件中，没有统一词表。
- 口语化表达集中在：首页菜单与 Snackbar、行程编辑说明文字、线路选择器提示、实时看板按钮、通知渠道描述、决策建议与演示回放。
- 部分字符串被逻辑依赖，不能随意改（见第五节），例如哨兵值 `"下车站"`、`"末班已过"`、`"未设置"`，以及 `LiveBoard.parseBig` 依赖的「约/待 + 数字 + 分/站/米/秒」格式。
- 现有单测对少量文案做了断言（`DecisionTest`、`CandidateServiceTest`），改名后需同步更新。

## 三、统一表达原则

1. **标题用名词短语**，不加疑问句、不省略主语。例：「在哪下车？」→「选择下车站」；「哪几天」→「生效日期」。
2. **按钮用动词短语**，2–4 字优先。例：「去开启」→「前往开启」；「结束」→「结束行程」。
3. **提示语先结论后动作**：说明发生了什么，再给出可执行动作。例：「生成回程失败：网络不通？」→「生成回程失败，请检查网络后重试」。
4. **统一术语**：行程、段、上车站、下车站、线路、通勤班车、时间范围、唤起、定位预热、常去地点。
5. **统一标点**：中文全角；引号统一用「」；省略号用「…」；并列用「、」，范围用「–」。
6. **统一数字与单位空格**：`N 分钟`、`N 站`、`N 米`、`HH:MM`（不写「分」作单位时用「分钟」）。
7. **去口语化**：删除「就行」「一下」「那班」「有点悬」「快跑」「该走了」等随意表达，保留信息量。

## 五、逻辑耦合与注意事项

1. **哨兵字符串不可改**：`CommuteService.legAlightName` 与 `MetroRoutes`、`TripEditor` 使用 `"下车站"` 作为「未设置」的哨兵；`Decision.END_OF_SERVICE` 与 `MockSource` 共用 `"末班已过"`；`Trip.title()` 的空值 `"未设置"` 被逻辑复用。以上保持原样。
2. **大号倒计时解析**：`LiveBoard.parseBig` 的正则要求 `^(约|待)?\s*(\d+)\s*((分|站|米|秒).*)$`。本次仅改「该走了/快到了/准备下车」等纯文字状态，不改 `约N分`、`N站`、`待N分` 的数字结构；若将 `待N分` 改为 `N 分后出发`，仅用于通知短文本，不进入 `headline`。
3. **站名高亮依赖**：`LiveBoard` 通过正则 `下一站\s*(?:就是\s*)?(\S+)` 提取站名并标黄。文案中必须保留「下一站」关键词。
4. **通知 ID 与 Action 不变**：只改通知渠道名称/描述与动作文字，不改 channel id、notification id、action intent。
5. **默认名称变更**：`"通勤车"` → `"通勤班车"`、`"通勤车上车点"` → `"通勤班车上车点"` 仅影响新建数据的默认值；已保存的行程不做数据迁移，保持用户原值。
6. **回程命名依赖**：`Reverse` 依据 `src.name.contains("上班")` 决定回程名，默认行程名 `"上班"` 不得修改。
7. **单测同步**：`DecisionTest.kt:182` 断言 `"暂无赶得上的车"`、`:187` 断言 `"下一班约 25 分钟"`，需随文案调整；`CandidateServiceTest.kt:42` 的 `scheduleText()` 文案未改动，无需调整。
