# 通勤胶囊：取消行程按钮（不产生行程记录）

## 概要

在「进行中的行程」卡片底部点击「结束行程」后的确认弹窗里，提供两个明确的结束方式：

- **结束并记录**：保持现有行为——结算节点、写入「最近行程」、保留学习样本。
- **取消行程**：停止本次行程，**不写入「最近行程」记录**，并**回滚本次已写入的学习样本**，等同于这次行程没发生过。

采用方案 C（收进结束确认弹窗），界面不新增按钮，避免误触，也让「记录 / 不记录」在最后一步被迫二选一。

```
点击「结束行程」后：

┌────────────────────────────────┐
│  结束本次行程？                 │
│  「取消行程」不会写入最近行程    │
│                                │
│  返回   [取消行程]  [结束并记录] │
└────────────────────────────────┘
```

- 通知栏「结束本次行程」走 `ActionReceiver.ACTION_STOP` → `userFinish()`，本次不新增取消入口。

## 改动清单

### 1. CommuteService：新增取消链路（核心）

文件：[CommuteService.kt](file:///e:/001-Program/CommuteCapsule/app/src/main/java/com/busnotice/commute/CommuteService.kt)

1. 新增 `fun userCancel()`（放在 `userFinish` 旁）：

```kotlin
/** 用户点「取消行程」：本次作废，不写记录、回滚学习样本 */
fun userCancel() {
    TraceLog.event("user_cancel", "leg" to legIdx, "riding" to riding)
    scope.launch(Dispatchers.Main) { loop?.cancel(); finish(cancelled = true) }
}
```

2. `finish()` 改为 `private fun finish(cancelled: Boolean = false)`，保留原有清理顺序，仅把「结算/学习」相关的调用按 `cancelled` 分支：

```kotlin
private fun finish(cancelled: Boolean = false) {
    if (finishing) return
    finishing = true
    if (cancelled) {
        // 本次作废：不沉淀站点/线路学习，不投票，不写最近行程
        metroRideOn = false
        busMovingOn = false
        runCatching { Learn.rollback(this, Learn.endJournal()) }
        NodeLog.clearActive(this)
        TraceLog.event("cancel", "leg" to legIdx, "riding" to riding)
    } else {
        // 原有逻辑原样保留
        runCatching { flushStopLearn(System.currentTimeMillis()) }
        if (metroRideOn) runCatching { endMetroRide() }
        if (busMovingOn) runCatching { busMovingOn = false; tacLearner?.let { it.endSurface(); MetroCells.save(this, it) } }
        if (!tail) placeVotes()
        settleNodes(aborted = !arrived && !tail)
    }
    // 之后的所有清理（stopChoices、holdCpu、WakeAlarm.cancel、AlarmBuzzer.stop、
    // TraceLog.stop、NodeLog.current、clearRun、移除定位、LiveState/LiveNotifier、
    // stopForeground、stopSelf）两条分支共用，保持现状
}
```

注意：

- `stopChoices.value = emptyList()`、`stopMarksUi.value = emptyList()`、`TraceLog.onCell = null`、`tail_end` 事件等原有语句位置不变。
- `TraceLog.event("finish", ...)` 增加 `"cancelled" to cancelled`，便于诊断。
- 取消分支**不调用** `settleNodes`，因此不会 `NodeLog.saveLastRun`，也就不会产生「最近行程」记录。

3. `companion object` 增加（与 `stop` 并列）：

```kotlin
/** 用户取消行程：本次作废，不写记录 */
fun cancel(ctx: Context) {
    val svc = instance
    if (svc != null) { svc.userCancel(); return }
    // 服务已不在：本来就不会有结算，只清残留
    ctx.getSharedPreferences("run_state", Context.MODE_PRIVATE).edit().clear().apply()
    LiveState.clearPersisted(ctx); LiveState.snapshot.value = null
    stopChoices.value = emptyList(); stopMarksUi.value = emptyList()
    LiveNotifier.clear(ctx)
    ctx.stopService(Intent(ctx, CommuteService::class.java))
}
```

## 假设与决策

- 采用**方案 C**（确认弹窗内二选一），不新增常驻按钮；这是用户选定的排版。
- 取消 = 完全作废：不写「最近行程」、不回填/学习节点、不投票家/公司、不保存地铁基站与路面基站学习；`Learn.rollback` 回滚本次日志内的样本。
- 取消后不主动清除 `Scheduler.markRan`（今天已跑标记）；这与现有「结束」一致，避免取消后立刻被定时器/围栏重新拉起形成循环。下次时间窗照常。
- 取消不修改行程本身（线路、起终点、时间范围都保留），只是这次运行不记录。
- 通知栏与流体云的「结束本次行程」仍等价于「结束并记录」，不新增取消入口（胶囊空间有限，且误触成本高）。
- 服务已被系统杀死时点取消，只需清理 `run_state` / 通知，本来也不会产生记录。
- 回滚依赖内存日志（`Learn.journal`）；若行程中途服务被杀并恢复，日志会丢失，此时取消只能保证不写记录、不新增学习，无法回滚恢复前已写的少量样本。这是既有机制的边界，不在本次改动范围内。
