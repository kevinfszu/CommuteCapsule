# 运行时导入线路数据（以广州地铁 11 / 13 号线为例）

## 摘要

目标：不重新编译 App，在「数据源」里直接导入一个 JSON 文件，就能使用广州地铁 11 号线、13 号线的站序、WGS-84 坐标、方向、首末班和发车间隔。导入后，地铁选方向、途经站数、剩余站数、到站提醒继续按现有引擎工作。

本次范围：

* 静态数据：线路、站点、方向、首末班、间隔、途经站。
* 不接实时来车，`RealtimeSource` 保持为空，引擎按「学到的时刻表 → 站距/间隔估算」降级。
* 数据来源为公开资料（OpenStreetMap + 广州地铁/政府公开信息），执行时核对运营区段与站名。

交付物：

1. 运行时 JSON 导入能力（主工程代码 + 「数据源」对话框入口）。
2. 可导入的 `data/guangzhou-11-13.json`。
3. `JsonTransit` 纯逻辑单元测试。
4. 文档与更新日志。

## 方案

### 1. 新增纯逻辑层 `JsonTransit.kt`

文件：`app/src/main/java/com/busnotice/commute/JsonTransit.kt`

职责：只做 JSON 解析和查询计算，不依赖 Android，便于 JVM 单元测试。

```kotlin
object JsonTransit {
    data class Stop(val name: String, val lat: Double, val lng: Double, val firstMin: Int?, val lastMin: Int?)
    data class Line(
        val id: String, val name: String, val subway: Boolean, val loop: Boolean,
        val dirLabel: String, val reverseId: String,
        val firstMin: Int, val lastMin: Int, val hopSec: Int,
        val stops: List<Stop>,
    )
    data class Doc(
        val region: String, val source: String, val updated: String,
        val lines: List<Line>,
    ) {
        val lineCount: Int get() = lines.map { it.name }.distinct().size
        val stationCount: Int get() = lines.flatMap { it.stops }.map { it.name }.distinct().size
    }

    fun parse(text: String): Doc
    fun search(doc: Doc, key: String, region: String): SearchResult
    fun lineDetail(doc: Doc, lineId: String, region: String): LineDetail
    fun nearbyStops(doc: Doc, lat: Double, lng: Double, region: String): List<NearStop>
    fun stationLines(doc: Doc, siteId: String, sameNameId: String, region: String): List<NearStop>
    fun subwayDirs(doc: Doc, lat: Double, lng: Double, stationName: String, region: String): List<SubwayDir>
    fun metroStops(doc: Doc, board: List<SubwayDir>, toLat: Double, toLng: Double, region: String): Int?
    fun metroRoute(doc: Doc, q: MetroQuery): MetroRoute?
}
```

解析规则：

* 根节点必须包含非空 `lines` 数组。
* 每条线路必须有唯一的 `id`、`name`、至少 2 个 `stops`。
* `lat`/`lng` 必须是合法经纬度，数据源统一 WGS-84。
* `subway` 默认 `false`；`loop` 默认 `false`；`reverseId` 可空。
* `first` / `last` 支持 `"HH:mm"`，线路级默认 `06:00` / `23:00`。
* `hopSec` 默认：地铁 140 秒，非地铁 90 秒，限制在 20–900 秒。
* 环线必须提供 `dirLabel`（如 `内环` / `外环`），否则报错，避免方向不明。
* 环线如果最后一个站与第一个站同名（闭合重复），解析时丢弃最后一个，保证站序唯一。
* 未知字段忽略，兼容现有模板 JSON。

查询规则：

* 名称归一化：去掉「地铁」和空格后再比较，避免「地铁13号线」与「13号线」对不上。
* `search`：线路按 `name` 分组，返回两个方向；站点按「站名 + 是否地铁」去重。
* `lineDetail`：按 `id` 返回该方向的完整站序；`reverseLineId` 原样返回。
* `nearbyStops` / `stationLines`：只用于公交，保持模板语义；`NearStop.lines` 只列非地铁线路。
* `subwayDirs`：
  * 先按站名精确匹配；匹配不到时在 800 米内找最近站名；
  * 返回该站经过的每条线路的每个方向；
  * `dest`：环线用 `dirLabel`（内环/外环），非环线用该方向终点站名；
  * `firstMin` / `lastMin` 取线路级配置，站点级可选覆盖；
  * `dirId` = 线路 `id`，`order` = 本站序号。
* `metroStops`：
  * 用 `dirId` 找方向线路，按目标坐标找最近站；
  * 环线：`hops = (to - from + n) % n`；
  * 非环线：仅当目标站序号大于上车站序号时返回差值；
  * 多个方向取最小正站数。
* `metroRoute`：
  * 线路名按归一化后的名称匹配；
  * 如果 `q.dir` 非空，优先选 `dirLabel` 或终点站名等于 `q.dir` 的方向；
  * 起终点先按站名精确匹配，再按坐标就近吸附（起点 1500 米、终点 3000 米内，超出返回 `null` 让引擎降级）；
  * 环线按所选方向的站序取前进路径（支持跨闭合点）；
  * 非环线只接受「终点在起点之后」的方向；
  * 返回 `MetroRoute(stations, hops * hopSec)`。

### 2. 新增运行时数据源 `ImportedJsonSource.kt`

文件：`app/src/main/java/com/busnotice/commute/ImportedJsonSource.kt`

```kotlin
object ImportedJsonSource : StaticSource {
    private const val FILE = "imported_transit.json"
    @Volatile private var doc: JsonTransit.Doc? = null

    val hasData get() = doc != null
    override val id = "imported"
    override val title get() = doc?.let {
        "导入的 JSON（${it.lineCount} 条线路 / ${it.stationCount} 站）"
    } ?: "导入的 JSON"

    fun load(ctx: Context): Boolean          // 启动时读 filesDir/imported_transit.json
    fun import(ctx: Context, text: String): JsonTransit.Doc  // 先解析校验，再原子写入
    fun clear(ctx: Context)                  // 删除文件并置空
    // 其余 StaticSource 方法全部委托 JsonTransit
}
```

实现要点：

* 文件固定写到 `context.filesDir/imported_transit.json`，不需要存储权限。
* 导入时先 `JsonTransit.parse(text)`；解析失败直接抛异常，旧数据不受影响。
* 写入用临时文件 + `renameTo`，避免写一半损坏。
* `load` 失败（文件损坏/格式错误）返回 `false`，不崩溃，回退到扩展源或演示城市。
* `doc` 用 `@Volatile` 保存，查询线程只读不可变对象。

### 6. JSON 格式扩展

在现有模板格式上做向后兼容扩展：

```json
{
  "region": "gz",
  "meta": {
    "source": "OpenStreetMap + 广州地铁公开信息",
    "updated": "2026-11-19",
    "note": "仅包含当前运营区段"
  },
  "lines": [
    {
      "id": "gz11-inner",
      "name": "11号线",
      "subway": true,
      "loop": true,
      "dirLabel": "内环",
      "reverseId": "gz11-outer",
      "first": "06:00",
      "last": "23:30",
      "hopSec": 140,
      "stops": [
        { "name": "赤沙", "lat": 23.0871855, "lng": 113.3583422 }
      ]
    }
  ]
}
```

字段说明：

| 字段                                           | 必填   | 说明                  |
| -------------------------------------------- | ---- | ------------------- |
| `region`                                     | 否    | 区域编号默认值，用户为空时写入     |
| `meta.source` / `meta.updated` / `meta.note` | 否    | 数据来源、日期、备注，仅展示/追溯   |
| `lines[].id`                                 | 是    | 唯一线路 ID             |
| `lines[].name`                               | 是    | 显示名，如 `11号线`、`13号线` |
| `lines[].subway`                             | 否    | 地铁写 `true`          |
| `lines[].loop`                               | 否    | 环线写 `true`          |
| `lines[].dirLabel`                           | 环线必填 | 方向名，如 `内环` / `外环`   |
| `lines[].reverseId`                          | 否    | 反方向线路 ID            |
| `lines[].first` / `last`                     | 否    | 线路首末班，`HH:mm`       |
| `lines[].hopSec`                             | 否    | 单站预计秒数，默认地铁 140     |
| `stops[].name`                               | 是    | 站名                  |
| `stops[].lat` / `lng`                        | 是    | WGS-84 坐标           |
| `stops[].first` / `last`                     | 否    | 站点级首末班覆盖            |

方向表示：

* 每个方向一条线路记录，两条记录共用 `name`，用 `reverseId` 互相指向。
* 非环线：两条记录站序相反，`dirLabel` 省略时默认取终点站名。
* 环线（11 号线）：两条记录站序相反，`loop: true`，`dirLabel` 分别为 `内环` / `外环`；不要重复写闭合站。

### 7. 数据文件 `data/guangzhou-11-13.json`

放置：`data/guangzhou-11-13.json`（用户导入文件）。

获取与生成步骤（执行时完成）：

1. 用 Overpass API（POST，带 User-Agent）取线路关系：
   * 11 号线外环：relation `18132492`（`地铁 11号线：外环`）
   * 11 号线内环：relation `18132493`（`地铁 11号线：内环`）
   * 13 号线：relation `6728313`（`天河公园 → 新沙`）、`7895352`（`新沙 → 天河公园`）
   * 查询必须用 `out body; >; out body;`；用 `out skel qt` 会丢掉站点名称（已实测）。
2. 解析 relation 的 `node` 成员（`role` 以 `stop` 开头），读取 `tags.name`、`lat`、`lon`。
3. 11 号线：
   * 内环实际返回 31 个 stop 成员，首尾都是「赤沙」，去重后 30 个运营站；
   * 与官方 31 站清单核对：广州火车站等是否已开通；只写当前实际停靠站，并在 `meta.note` 标注；
   * 外环由内环站序反转生成，或直接取外环 relation 核对；
   * `dirLabel` 写 `内环` / `外环`，`loop: true`。
4. 13 号线：
   * OSM 当前关系覆盖「天河公园—新沙」；2025-09-29 已开通天河公园—鱼珠段；
   * 2025 年底计划开通鸦岗—天河公园西段；执行时先核对官方是否已开通：
     * 已开通：按广州地铁/广州市政府公告的 19 站顺序补到「天河公园」之前，坐标用 OSM 同名站节点；
     * 未开通或无法核实：只写当前运营区段，并在 `meta.note` 明确「仅东段」。
   * 站名以官方公布名为准（OSM 可能仍是旧名，如「流花」对应「流花路」等），逐站核对后统一。
5. 首末班：
   * 能从官方时刻表取到线路级首末班就写入；
   * 取不到就用默认 `06:00` / `23:00`，并在 `meta.note` 标注「首末班为估算」。
6. 单站用时：
   * 有官方全程用时则 `hopSec = 全程秒数 / 站数`；
   * 否则 11 号线用 140 秒、13 号线用 140 秒，后续由 App 学习实测修正。
7. 校验：
   * 站名在每条线路内唯一，站数符合官方/运营区段；
   * 坐标落在广州范围（纬度 22.5–23.9，经度 112.9–114.1）；
   * 相邻站距离 300 米–8 公里；
   * 11 号线首尾站距离合理（闭合），且不重复写闭合站；
   * `ConvertFrom-Json` / `JSON.parse` 能正常解析。
8. 数据许可：
   * OSM 数据遵循 ODbL，使用时保留 `meta.source` 署名；
   * 仓库本身声明不包含真实数据，因此把 `data/` 加入 `.gitignore`，只作为本地个人数据使用；如需发布请自行确认许可并替换为自有数据。

## 假设与决策

* 运行时导入优先于 `src/extra`；删除导入后回退扩展源，再回退演示城市。
* 本次只做静态数据，`realtime` 在导入模式下为 `null`。
* 环线用「两条方向记录 + `loop: true` + `dirLabel`」表示；不引入新的线路类型。
* 首末班以线路级为主，站点级字段预留但本次广州数据不逐站填写。
* 站名比较先精确、再去「站」、再包含；坐标吸附有最大距离，避免把远离线路的目的地硬套到线上。

* 已保存的旧行程如果引用了演示城市或其他数据源，不做自动迁移；导入后重新选一次线路即可。

## 验证

### 自动验证

1. JSON 数据文件：
   * PowerShell `Get-Content data/guangzhou-11-13.json -Raw | ConvertFrom-Json` 解析通过；
   * 校验 11 号线站数、13 号线站数、坐标范围、相邻距离。

### 手动验证（Android 12+）

1. 安装 Debug APK，打开 App → 右上菜单 →「数据源」。
2. 点「导入 JSON 文件」，选择 `data/guangzhou-11-13.json`，确认提示「已导入 2 条线路、N 个站」。
3. 新建地铁段：
   * 搜「天河公园」或「体育西路」，选择 11 号线，确认出现「开往 内环 / 开往 外环」；
   * 搜「鱼珠」或「新沙」，选择 13 号线，确认出现两个终点方向；
   * 选下车站后保存，编辑页应显示「自动：A → B，共 N 站，约 X 分钟」。
4. 杀进程重开，确认导入数据仍在，「数据源」显示「导入的 JSON（2 条线路 / N 站）」。
5. 点「删除导入数据，恢复默认」，确认回到「演示城市（虚构数据）」，原有演示流程可走通。
6. 回归：公交搜索、附近站点、演示回放不受影响。

## 风险与注意事项

* **真实数据准确性**：11 号线广州火车站/广州东站是否停靠、13 号线西段是否开通，必须以执行当天官方信息为准；不确定时只写已确认运营区段并在 `meta.note` 说明。
* **站名差异**：OSM 与官方站名可能不一致（如「流花」/「流花路」），需逐站核对；站名不一致会导致搜索和方向显示对不上。
* **环线方向**：内环/外环的顺时针定义来自 OSM relation 名称；如官方定义不同，以官方为准调整 `dirLabel` 与站序。
* **首末班误差**：线路级首末班不是逐站首末班，App 的「下一班」会有偏差；坐满 3 次后会改用实测用时，但班次仍按配置估算。
* **导入时正在行程**：`Transit.static` 会立即切换，但服务内已缓存的 `metroDirs` / `metroRoutes` 可能仍是旧数据；UI 提示用户结束并重新开始行程。
* **数据许可**：OSM 为 ODbL；广州地铁时刻/站名等公开信息的使用需自行确认。仓库保持「不含真实数据」原则，`data/` 不提交。
